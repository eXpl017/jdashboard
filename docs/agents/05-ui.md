# Phase 4 — The web UI

**Goal:** one page that answers "what is new?" in a glance, with filters that
match the questions a relocating engineer actually asks.

## What was built

- `app/templates/base.html` and `index.html` — semantic markup: header,
  summary cards, filter form, job list, refresh panel, footer, and a
  `<template>` for the job card.
- `app/static/app.css` — CSS variables, light and dark mode via
  `prefers-color-scheme`, responsive down to a phone, visible focus rings.
- `app/static/app.js` — vanilla JS: fetch sources/stats/jobs, debounced
  filter reloads, URL state, refresh polling, and empty/loading/error states.
- `GET /` serves the page; `/static` serves the assets. No CDN, no framework,
  no build step.

## API gaps found while building the UI

The API was built in Phase 1 for a programmatic consumer. The UI needed three
things it did not have:

1. **`GET /api/sources`** — per-source metadata plus the last refresh status,
   derived from the latest `ScrapeSourceResult`.
2. **`GET /api/stats` with filters** — so the summary cards describe the
   current view rather than the whole database.
3. **`source_name` on each job** — the UI shows "Michael Page Japan", not
   `michael_page`.

All three were added in this phase, with tests.

## Design decisions

- **The summary cards match the filters.** "Jobs", "New in window", "Sources",
  and "Last run" describe what you are looking at.
- **Badges instead of sorting.** Visa and overseas eligibility are shown as
  badges; the list stays sorted newest first.
- **Empty states explain themselves.** "No jobs found" plus the reason (the
  window, the role filter, the location scope) and what to change.
- **The refresh panel is always visible** and shows per-source status and
  counts, so a failing source is obvious without opening the logs.
- **Job data is inserted with `textContent`**, never `innerHTML`, so a
  malicious listing cannot inject markup.
- **Timestamps are shown in JST**, computed client-side from the UTC values
  the API returns.

## Accessibility

- Every control has a `<label>`; the skip link is the first focusable
  element.
- The job list is an `aria-live="polite"` region; the refresh status line is
  too.
- Job details use `<details>`/`<summary>`, so they work with the keyboard.
- Colour is never the only signal: every badge has text.
